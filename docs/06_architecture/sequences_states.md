### Общие правила сценариев

1. **Время.** Хранится в UTC, показывается в часовом поясе получателя с указанием пояса (BR-SCHED-01, BR-NOTIF-05). Команды планировщика и календарный месяц супервизии считаются по московскому времени (DEC-37).
2. **События.** Модуль меняет свои данные и в той же транзакции пишет доменное событие в outbox; подписчики получают его через очередь Redis «как минимум один раз» и обрабатывают идемпотентно. На диаграммах доставка события показана одной стрелкой.
3. **Письма.** NOTIF ставит письмо в очередь `mail-transactional` и пишет уведомление в центр уведомлений; письмо уходит по SMTP на почтовый сервер. В письмах нет сведений о состоянии (BR-NOTIF-04). Если письмо не ушло после повторов, процесс не останавливается (BR-NOTIF-09).
4. **Деньги.** Модули работают с деньгами только через публичные сервисы PAY и PAYOUT. У каждой операции есть ключ идемпотентности; вебхуки проверяются по подписи и пишутся в inbox до обработки. Скидка по промокоду уменьшает только долю платформы, психологу начисляется 70 % полной цены (DEC-57).
5. **Машины состояний.** Каждый переход пишет запись в историю сущности и доменное событие; недопустимый переход отклоняет доменная модель модуля-владельца. Значения параметров, действовавшие в момент события, сохраняются в сущности.
6. **Допущения по открытым вопросам.** Q-43 — какой платёжный сервис подключается; Q-52 — все возвраты зачисляются на баланс личного кабинета, при оплате сначала расходуется баланс, затем карта, остаток выводится на карту по заявке клиента; Q-53 — требование супервизии действует на супервизоров, которые ведут клиентов; Q-54 — второй участник парной сессии приходит по приглашению со своей учётной записью; Q-56 — при неявке клиента и отмене клиентом после списания психологу начисляется 70 %, при возврате по жалобе начисление сторнируется.
7. **Формат.** Последовательность: участники и предусловия → диаграмма, шаги пронумерованы → ошибки и исключения → связанные правила. Машина состояний: диаграмма → таблица переходов «из → событие → в, условия, кто инициирует». ID `SEQ-NN` и `ST-NN` действуют внутри документа. Перед каждой диаграммой стоит комментарий с именем исходника в папке [diagrams](diagrams/README.md).

# A. Последовательности

## SEQ-01. Подбор, регистрация и привязка карты

**Участники:** клиент, психолог, Next.js (SITE-06, WIZ-01…WIZ-07), Laravel API (MATCH, SCHED, AUTH, CONSENT, BOOK, PAY, PROMO, NOTIF), очередь Redis, платёжный адаптер или эмулятор, почтовый сервер. **Этап ТЗ:** Э3.
**Предусловия:** клиент пришёл с посадочной по запросу, главной или статьи. Путь через Германа (WIZ-02b) описан в SEQ-14 и возвращается в этот сценарий на шаге подбора; путь через каталог начинается с выбора времени.

<!-- diagram: seq_01_booking_card -->
```mermaid
sequenceDiagram
  autonumber
  actor C as Клиент
  participant WEB as Next.js
  participant API as Laravel API
  participant Q as Очередь Redis
  participant PAY as Платёжный адаптер или эмулятор
  participant MAIL as Почтовый сервер
  actor P as Психолог

  C->>WEB: посадочная по запросу или WIZ-01, анкета WIZ-02a
  Note over C,WEB: ответы хранятся в браузере до регистрации и не передаются в Метрику
  WEB->>API: ответы анкеты, MATCH
  API->>API: отбор по BR-MATCH-02 и ранжирование по BR-MATCH-03
  API-->>WEB: главная рекомендация и все альтернативы, причины текстом
  C->>WEB: выбирает психолога и слот WIZ-04
  WEB->>API: удержать слот, SCHED
  alt слот занят
    API-->>WEB: отказ и ближайшие свободные слоты
  else слот свободен

  end
  C->>WEB: регистрация WIZ-05, email, пароль, согласие на обработку ПДн, 18+
  WEB->>API: создать учётную запись, AUTH и CONSENT
  API->>API: учётная запись «Email не подтверждён», удержание продлено на P-SLOT-HOLD-EMAIL
  API->>Q: письмо со ссылкой подтверждения email
  Q->>MAIL: отправка по SMTP
  MAIL-->>C: письмо подтверждения
  C->>WEB: переход по ссылке, возврат на WIZ-06
  WEB->>API: подтвердить email, проверить слот
  API-->>WEB: сводка, цена, момент автосписания, правила отмены
  C->>WEB: промокод или код сертификата, оферта, согласие на автосписание
  WEB->>API: начать привязку карты, PAY
  API->>PAY: начать привязку карты с ключом операции
  PAY-->>API: параметры платёжной формы
  API-->>WEB: параметры формы
  C->>PAY: данные карты в форме сервиса или эмулятора, 3-D Secure
  PAY->>API: вебхук «Карта привязана», токен и маска
  API->>API: проверка подписи, inbox, токен сохранён зашифрованно
  WEB->>API: создать запись, BOOK, ключ идемпотентности
  alt до начала больше P-CHARGE-OFFSET
    API->>API: сессия «Забронирована», цена и скидка зафиксированы
    API->>API: задание на списание со сроком за P-CHARGE-OFFSET до начала
  else до начала меньше P-CHARGE-OFFSET
    API->>API: сначала расход баланса клиента, допущение Q-52
    API->>PAY: оплатить остаток с участием клиента и 3-D Secure
    PAY-->>API: оплата успешна
    API->>API: сессия «Оплачена», чек PREPAYMENT_FULL
  end
  API->>Q: событие book.session.booked, письма клиенту и психологу
  API-->>WEB: запись подтверждена, WIZ-07
  Q->>MAIL: отправка по SMTP
  MAIL-->>C: день и время в часовом поясе клиента, ссылка на вход в кабинет
  MAIL-->>P: новая запись
```

| Ситуация | Поведение | Основание |
|---|---|---|
| Слот занят или удержание истекло | Отказ и ближайшие свободные слоты; после перехода по ссылке из письма слот проверяется заново | BR-BOOK-02, BR-ACC-08 |
| Email не подтверждён | Привязка карты и создание записи недоступны; повторное письмо — не чаще `P-EMAIL-RESEND-INTERVAL` | BR-ACC-03, BR-ACC-08 |
| Клиенту нет 18 лет | Регистрация и запись не выполняются | DEC-49 |
| Подходящих психологов нет | Клиент видит условия, которые сузили выбор, и может смягчить их, перейти в каталог или к Герману | BR-MATCH-06 |
| Привязка карты не удалась или форма закрыта | Событие «Привязка не удалась», причина на WIZ-06; запись не создаётся, слот удерживается до конца срока | BR-PAY-01, BR-BOOK-04 |
| Запись меньше чем за `P-CHARGE-OFFSET`, оплата отклонена | Запись не создаётся, клиенту предлагается другая карта; расход баланса отменяется обратной проводкой [допущение Q-52] | BR-BOOK-04 |
| Превышен лимит предстоящих сессий у психолога | Отказ с объяснением | BR-BOOK-05 |
| Корпоративный сотрудник с остатком лимита | Привязка карты пропускается, сессия помечается «оплачивает компания» (SEQ-20) | BR-BOOK-01, BR-B2B-04 |
| Парная сессия | Клиент указывает email второго участника; приглашение уходит письмом, вход — со своей учётной записью (SEQ-07) [допущение Q-54] | BR-BOOK-16 |
| Письмо не отправлено после всех повторов | Запись действует, уведомление остаётся в центре уведомлений CL-14 | BR-NOTIF-09 |

**Связанные правила:** DEC-15, DEC-16, DEC-38, DEC-49, BR-MATCH-01…BR-MATCH-07, BR-ACC-02, BR-ACC-08, BR-BOOK-01…BR-BOOK-06, BR-PAY-01, BR-PAY-02, BR-PROMO-05; параметры `P-SLOT-HOLD`, `P-SLOT-HOLD-EMAIL`, `P-CHARGE-OFFSET`.

## SEQ-02. Автосписание за 12 часов

**Участники:** планировщик, очередь Redis, Laravel API (PAY, BOOK, PROMO, NOTIF), платёжный адаптер или эмулятор, почтовый сервер, клиент, психолог. **Этап ТЗ:** Э3.
**Предусловия:** сессия «Забронирована», задание на списание создано по событию `book.session.booked` со сроком за `P-CHARGE-OFFSET` до начала и крайним сроком за `P-CHARGE-DEADLINE` до начала. Сумма — цена, зафиксированная при записи, за вычетом скидки промокода.

```mermaid
  end
  Q->>API: задача списания, очередь payments
  API->>API: блокировка задания, проверка сессии, карты и согласия на автосписание
  alt согласие отозвано или карты нет
    API->>Q: письмо со ссылкой на привязку карты в CL-07
  else проверки пройдены
    API->>API: при первой попытке расход баланса клиента, допущение Q-52
    alt баланс покрывает всю сумму
      API->>API: задание «Выполнено», сессия «Оплачена»
    else остаток оплачивается картой
      API->>PAY: запросить статус по ключу операции
      PAY-->>API: операция не найдена
      API->>PAY: списать по токену, ключ из ID задания и номера попытки
      alt успех
        PAY-->>API: успешна
        PAY->>API: вебхук «Оплата успешна»
        API->>API: inbox, платёж «Проведён», задание «Выполнено», сессия «Оплачена»
        API->>PAY: чек прихода PREPAYMENT_FULL
        API->>Q: письмо о списании со ссылкой на чек
      else отказ с категорией «повторять»
        PAY-->>API: отклонена
        API->>API: задание «Ожидает повтора», следующая попытка по P-CHARGE-RETRY
        API->>Q: письмо «не удалось списать, обновите карту»
      else отказ «не повторять» или «нужна другая карта»
        PAY-->>API: отклонена без повторов
        API->>Q: письмо со ссылкой на оплату другой картой в CL-07
      else таймаут или ошибка сервиса
        PAY-->>API: статус неизвестен
        API->>PAY: запрос статуса и технический повтор с тем же ключом
      end
    end
  end
  Q->>MAIL: отправка писем
  MAIL-->>C: списание прошло или просьба обновить карту
  opt клиент оплачивает другой картой в CL-07 до крайнего срока
    C->>API: оплата с участием клиента
    API->>PAY: оплатить с участием плательщика, 3-D Secure
    PAY->>API: вебхук «Оплата успешна»
    API->>API: задание «Выполнено», сессия «Оплачена», чек
  end
  opt наступил P-CHARGE-DEADLINE, оплаты нет
    SCH->>Q: задача крайнего срока
    Q->>API: закрыть задание
    API->>API: сторно расхода баланса, задание «Не выполнено окончательно»
    API->>API: сессия «Отменена системой», слот освобождён, промокод восстановлен
    API->>Q: событие pay.charge.failed_final, письма
    Q->>MAIL: отправка
    MAIL-->>C: сессия отменена без удержаний, можно записаться снова
    MAIL-->>P: сессия отменена, слот свободен
  end
```

| Ситуация | Поведение | Основание |
|---|---|---|
| Повторный или запоздавший вебхук | Ответ 2xx без повторной обработки; второе успешное списание по сессии невозможно | BR-PAY-06 |
| Вебхук потерян, задание зависло в обработке | Команда `pay:recover-stuck-charges` каждые 5 мин запрашивает статус операции у сервиса | BR-PAY-13 |
| Клиент удалил карту или отказался от автосписаний | Токен больше не используется, клиенту предлагается привязать другую карту; без оплаты к `P-CHARGE-DEADLINE` сессия отменяется без удержаний | BR-PAY-09 |
| Клиент отменил сессию до успешного списания | Задание «Отменено», расход баланса сторнируется, отмена бесплатна (SEQ-03) | BR-CANC-01 |
| Скидка покрывает всю цену | Списание не выполняется, в срок задания сессия получает статус «Оплачена» | BR-PROMO-08 |
| Корпоративная сессия в пределах лимита | Задания на списание нет; в срок `P-CHARGE-OFFSET` списывается лимит сотрудника (SEQ-20) | BR-B2B-05 |
| Массовый сбой платёжного сервиса | Повторы до крайнего срока; Супер-администратор может отложить автоотмену неоплаченных сессий [Рек.] | BR-PAY-05 |
| Реальный сервис ещё не подключён | Все вызовы обслуживает тестовый эмулятор с теми же статусами, категориями отказа и вебхуками | DEC-38 |

**Связанные правила:** DEC-22, DEC-23, DEC-38, Q-52, BR-PAY-04…BR-PAY-07, BR-PAY-09, BR-PAY-13, BR-PROMO-08, BR-PROMO-09, BR-B2B-05; параметры `P-CHARGE-OFFSET`, `P-CHARGE-RETRY`, `P-CHARGE-DEADLINE`.

## SEQ-03. Перенос и отмена клиентом

**Участники:** клиент, психолог, Next.js (CL-03), Laravel API (BOOK, SCHED, PAY, PROMO, PAYOUT, MEET, NOTIF), очередь Redis, TetaMeet, почтовый сервер. **Этап ТЗ:** Э3.
**Предусловия:** сессия «Забронирована» или «Оплачена» и ещё не началась. Интерфейс получает от API вычисленные признаки: списана ли оплата, до какого времени отмена бесплатна, какие слоты доступны для переноса.

<!-- diagram: seq_03_client_reschedule_cancel -->
```mermaid
sequenceDiagram
  autonumber
  actor C as Клиент
  participant WEB as Next.js
  participant API as Laravel API
  participant Q as Очередь Redis
  participant TM as TetaMeet
  participant MAIL as Почтовый сервер
  actor P as Психолог

  C->>WEB: CL-03, перенести или отменить сессию
  WEB->>API: доступные действия, BOOK
  API-->>WEB: оплата списана или нет, срок бесплатной отмены, слоты
  alt перенос до списания
    C->>WEB: новый свободный слот того же психолога
    WEB->>API: перенести, ключ идемпотентности
    API->>API: удержание нового слота, новое время сессии «Забронирована»
    API->>API: срок задания на списание пересчитан от нового начала
    opt новое начало ближе P-CHARGE-OFFSET
      API->>API: списание сразу, как в SEQ-01
    end
  else отмена до списания
    C->>WEB: отменить
    WEB->>API: отменить, BOOK
    API->>API: сессия «Отменена клиентом», задание на списание «Отменено»
    API->>API: слот освобождён, применение промокода восстановлено
  else перенос после списания
    C->>WEB: новый свободный слот того же психолога
    WEB->>API: перенести
    API->>API: проверка по времени сервера, новое начало не раньше чем через 12 ч
    alt условие DEC-56 выполнено
      API->>API: оплата и чек переходят на новое время, статус «Оплачена» сохраняется

    else новое начало раньше чем через 12 ч
      API-->>WEB: отказ и слоты не раньше чем через 12 ч
    end
  else отмена после списания
    API-->>WEB: предупреждение, что оплата не вернётся, и предложение переноса
    C->>WEB: подтверждает отмену
    WEB->>API: отменить
    API->>API: сессия «Отменена клиентом», полное удержание оплаты
    API->>API: промокод не восстанавливается, слот освобождён
    API->>API: начисление психологу 70 процентов, допущение Q-56
  end
  API->>TM: изменить или закрыть комнату, если она создана
  API->>Q: событие book.session.rescheduled или book.session.cancelled, письма
  Q->>MAIL: отправка
  MAIL-->>C: новое время или подтверждение отмены
  MAIL-->>P: перенос или отмена записи
```

| Ситуация | Поведение | Основание |
|---|---|---|
| Сессия уже началась | Перенос и отмена недоступны; дальше действуют итоговые статусы SEQ-07 | BR-CANC-10 |
| Новый слот занят | Отказ и ближайшие свободные слоты | BR-BOOK-02 |
| Перенос после списания на время раньше чем через 12 ч | Отказ; клиент выбирает другой слот или оставляет исходное время | DEC-56 |
| Отмена после списания | Полное удержание; клиент может подать жалобу на списание (SEQ-06) | DEC-23, BR-CANC-03, BR-CANC-05 |
| Число переносов | До списания не ограничено; после списания ограничено только условием DEC-56 [П] | BR-CANC-02, BR-CANC-04 |

| Корпоративная сессия | До `P-CHARGE-OFFSET` отмена сохраняет лимит; после — сессия засчитывается в лимит | BR-B2B-05, BR-CANC-11 |
| Отмена при смене психолога | Отдельный сценарий с зачислением оплаты на баланс (SEQ-04) | DEC-48 |

**Связанные правила:** DEC-23, DEC-56, Q-56, BR-CANC-01…BR-CANC-05, BR-CANC-10, BR-CANC-11, BR-PROMO-09, BR-PAYOUT-02, BR-PRICE-04; параметр `P-CHARGE-OFFSET`.

## SEQ-04. Смена психолога

**Участники:** клиент, прежний психолог, Next.js (CL-04, WIZ-02a…WIZ-07), Laravel API (BOOK, PAY, PROMO, B2B, MATCH, NOTIF), очередь Redis, почтовый сервер. **Этап ТЗ:** Э3.
**Предусловия:** у клиента есть назначенные, но не проведённые сессии с прежним психологом, или клиент просто хочет выбрать другого специалиста. Смена психолога бесплатна и не ограничена по числу.

<!-- diagram: seq_04_change_psychologist -->
```mermaid
sequenceDiagram
  autonumber
  actor C as Клиент
  participant WEB as Next.js
  participant API as Laravel API
  participant Q as Очередь Redis
  participant MAIL as Почтовый сервер
  actor P as Прежний психолог

  C->>WEB: CL-04, сменить психолога
  WEB->>API: назначенные непроведённые сессии с прежним психологом
  API-->>WEB: список сессий и необязательный вопрос о причине
  C->>WEB: отмечает сессии для отмены
  WEB->>API: отменить выбранные, ключ идемпотентности
  loop каждая выбранная сессия
    alt оплата не списана
      API->>API: сессия «Отменена клиентом», задание на списание «Отменено»
    else оплата списана
      API->>API: сессия «Отменена клиентом» с причиной «смена психолога»
      API->>API: вся оплата сессии зачислена на баланс личного кабинета, DEC-48
    else сессия в пределах корпоративного лимита
      API->>API: сессия отменена, лимит сотрудника восстановлен
    end
    API->>API: слот освобождён, применение промокода восстановлено
  end
  API->>Q: события book.session.cancelled и pay.balance.credited, письма
  Q->>MAIL: отправка
  MAIL-->>P: отмена записей, причина смены не передаётся
  MAIL-->>C: отмена сессий и остаток баланса
  C->>WEB: повторная анкета WIZ-02a
  WEB->>API: новая анкета заменяет прежнюю для подбора, MATCH
  API-->>WEB: главная рекомендация и все альтернативы
  C->>WEB: новый психолог и слот
  WEB->>API: запись, как в SEQ-01, карта уже привязана
  API->>API: сессия «Забронирована», при списании сначала баланс, допущение Q-52
  API->>Q: событие book.session.booked, письмо-подтверждение
  Q->>MAIL: отправка
  MAIL-->>C: день и время сессии, ссылка на вход в кабинет
```

| Ситуация | Поведение | Основание |
|---|---|---|
| Клиент не отменяет назначенные сессии | Сессии с прежним психологом сохраняются и проводятся по общим правилам | BR-MATCH-10 |
| Оплата сессии уже списана, до начала меньше 12 ч | Оплата зачисляется на баланс: для смены психолога действует DEC-48, а не полное удержание DEC-23 [П] | DEC-23, DEC-48 |
| Сессия уже началась | Отмена недоступна | BR-CANC-10 |
| Часть оплаты была списана с баланса | На баланс зачисляется вся оплата сессии — и часть с баланса, и часть с карты [допущение Q-52] | Q-52 |
| Начисление прежнему психологу | Не создаётся: сессия не проведена, оплата возвращена клиенту на баланс | BR-PAYOUT-01 |
| Клиент хочет вернуть деньги на карту | Заявка на вывод остатка в CL-07 (ST-04) [допущение Q-52] [ЮРИСТ] | Q-52 |
| Доступ нового психолога к истории | Новый психолог не видит историю сессий клиента с прежним | BR-RBAC-08 |
| Клиент прошёл анкету, но не записался | Новая анкета сохраняется для подбора, записи не меняются | BR-MATCH-09 |

## SEQ-05. Отмена или неявка психолога

**Участники:** психолог, клиент, администратор, Next.js (PRO-04, CL-03, CL-12, ADM-04, ADM-19), Laravel API (BOOK, MEET, PAY, PROMO, PAYOUT, SUPPORT, NOTIF), очередь Redis, планировщик, TetaMeet, почтовый сервер. **Этап ТЗ:** Э2, Э3.
**Предусловия:** сессия «Забронирована» или «Оплачена». Отмену психолог выполняет до начала сессии; неявка фиксируется, если психолог не вошёл в комнату в течение `P-NOSHOW-WAIT` после начала по журналу сессий.

<!-- diagram: seq_05_psychologist_cancel_noshow -->
```mermaid

  autonumber
  actor P as Психолог

  actor A as Администратор

  participant Q as Очередь Redis
  participant SCH as Планировщик
  participant TM as TetaMeet
  participant MAIL as Почтовый сервер

  alt психолог отменяет сессию до начала
    P->>WEB: PRO-04, отменить сессию
    WEB->>API: отменить, BOOK

    API->>Q: письмо клиенту с выбором возврата или переноса
    Q->>MAIL: отправка

      API->>API: полная оплата зачислена на баланс, допущение Q-52

      WEB->>API: свободный слот того же психолога
      API->>API: новая сессия «Оплачена», оплата и чек переходят на неё
    else клиент не выбрал до крайнего срока
      SCH->>Q: крайний срок выбора
      Q->>API: зачислить полную оплату на баланс, допущение Q-52
    end

  end

    API->>API: обращение в очереди ADM-19 с данными журнала сессий, SEQ-14
    alt часы дежурства 10:00–20:00 МСК
      API-->>A: уведомление в реальном времени
```

|---|---|---|
| Психолог отменяет сессию меньше чем за `P-CHARGE-OFFSET` | Отмена фиксируется как инцидент качества; при `P-QUALITY-INCIDENT-THRESHOLD` администратору создаётся задача на разбор; денежных удержаний с психолога нет | BR-CANC-08 |
| Журнал сессий противоречит отметке клиента | Итоговый статус ставит администратор по журналу сессий в ADM-04 | BR-CANC-07, BR-RBAC-10 |
| Психолог вошёл, но связь оборвалась | Сценарий технической проблемы: при длительности меньше `P-AUTO-COMPLETE-MIN` клиент выбирает перенос или возврат, начисления нет (SEQ-07) | BR-BOOK-15 |
| Клиент не выбрал возврат или перенос | При отмене — полный возврат на баланс в исходное время начала; при неявке — через `P-OUTCOME-DEADLINE` после начала [Рек.] | BR-CANC-06 |
| Корпоративная сессия | Вместо денежного возврата восстанавливается лимит сотрудника | BR-B2B-05, BR-CANC-11 |
| Статус исправлен после выплаты начисления | Отрицательная корректировка удерживается из следующих начислений (ST-06) | BR-PAYOUT-12 |
| Психолог заблокирован или покинул платформу | Предстоящие сессии отменяются по инициативе платформы с полным возвратом | BR-CANC-09, BR-ACC-17 |
| Вопрос не требует администратора | Герман отвечает сам; администратору передаются только очень сложные случаи | DEC-54 |

**Связанные правила:** DEC-23, DEC-54, Q-52, BR-CANC-06…BR-CANC-09, BR-BOOK-15, BR-PROMO-09, BR-AIBOT-06, BR-PAYOUT-01; параметры `P-NOSHOW-WAIT`, `P-OUTCOME-DEADLINE`, `P-QUALITY-INCIDENT-THRESHOLD`.

## SEQ-06. Жалоба на списание

**Участники:** клиент, администратор, Next.js (CL-07, ADM-07, ADM-19), Laravel API (PAY, PAYOUT, SUPPORT, NOTIF), очередь Redis, планировщик, почтовый сервер. **Этап ТЗ:** Э3, Э4.
**Предусловия:** оплата по сессии списана и удержана — после отмены клиентом, неявки клиента или проведённой сессии, с которой клиент не согласен.

```mermaid

    API->>API: событие aibot.dialog.handover_requested
    API->>API: SUPPORT, обращение с историей диалога в очереди ADM-19
    API-->>WEB: статус «Передано администратору», Герман в обращении не отвечает
    alt часы дежурства 10:00–20:00 МСК
      API-->>A: уведомление в реальном времени
      A->>WEB: подключается к той же переписке
    else вне часов дежурства
      API-->>WEB: когда ответит администратор, в часовом поясе пользователя
      A->>API: ответ в начале следующего дежурства
      API->>Q: письмо, если пользователь не в сети
      Q->>MAIL: отправка
      MAIL-->>C: ответ администратора ждёт в виджете
    end
    A->>API: закрыть обращение
    API-->>WEB: диалог снова ведёт Герман
  end
```

| Ситуация | Поведение | Основание |
|---|---|---|
| Обычный или организационный вопрос | Герман отвечает сам, передачи нет | DEC-54, BR-AIBOT-02 |
| В базе знаний нет ответа | Герман сообщает об этом и не придумывает ответ; после `P-AIBOT-FALLBACK-COUNT` таких ответов подряд предлагает передать вопрос администратору | BR-AIBOT-04 |
| Признаки кризиса вне часов дежурства | Ссылка на SITE-15 показывается сразу в любое время; обращение с отметкой «срочно» стоит первым в очереди к началу дежурства | BR-AIBOT-05, DEC-54 |
| Ответ модели не прошёл проверку | Шаблонный ответ с просьбой уточнить вопрос или заполнить анкету | BR-AIBOT-03 |
| Просьба записать, перенести или отменить сессию | Герман не выполняет действие сам и даёт кнопку перехода к нему | BR-AIBOT-08 |
| Неявка психолога или возврат денег | Очень сложный вопрос: передача администратору (SEQ-05, SEQ-06) | DEC-14, DEC-54 |
| Превышен `P-AIBOT-RATE-LIMIT` | Герман предлагает обратиться в техподдержку | BR-AIBOT-12 |
| Передачу запросил гость | Герман просит email для ответа и согласие на обработку ПДн | BR-AIBOT-10 |
| Сведения о состоянии в диалоге | Не передаются в Метрику и в логи; в модель уходит текст с замаскированными контактами | BR-PRIV-03, BR-PRIV-04 |
| Герман выключен в ADM-26 или модель недоступна | Виджет предлагает анкету и техподдержку | DEC-54 |

**Связанные правила:** DEC-13, DEC-14, DEC-54, BR-AIBOT-01…BR-AIBOT-06, BR-AIBOT-08…BR-AIBOT-12, BR-MATCH-01, BR-SUPPORT-01, BR-PRIV-03; параметры `P-AIBOT-RATE-LIMIT`, `P-AIBOT-FALLBACK-COUNT`, `P-AIBOT-DIALOG-TTL`.

## SEQ-15. Обращение в техподдержку

**Участники:** клиент или психолог, администраторы, Next.js (CL-12, PRO-17, ADM-19), Laravel API (SUPPORT, FILES, NOTIF), очередь Redis, планировщик, почтовый сервер. **Этап ТЗ:** Э11.
**Предусловия:** пользователь вошёл в кабинет. Отдельной роли оператора нет — обращения обрабатывают администраторы; виджет собственный (DEC-09).

```mermaid
sequenceDiagram
  autonumber
  actor U as Клиент или психолог

  participant API as Laravel API
  participant Q as Очередь Redis
  participant SCH as Планировщик
  actor A as Администратор
  actor A2 as Другой администратор

  WEB->>API: SUPPORT и FILES
  API->>Q: антивирусная проверка вложений

    API->>API: сообщение добавлено в открытое обращение
  else открытого обращения нет

  end

  API->>Q: письмо администраторам не в сети

  opt передача другому администратору
    A->>API: передать с внутренним комментарием
    API-->>A2: обращение назначено
  end
```

## SEQ-18. Подарочный сертификат

# B. Машины состояний

Для каждой сущности — диаграмма и таблица переходов. Состояния названы так, как их видят пользователи в интерфейсе; технические коды статусов задаёт [модель данных](data_model.md). Недопустимый переход отклоняет доменная модель модуля-владельца; каждый переход пишет историю сущности и доменное событие (раздел 0). В колонке «Кто инициирует» «Система» — команда планировщика, обработчик очереди или вебхук.

| Лимит исчерпан | Начался новый период лимита или лимит восстановлен после отмены или неявки психолога | Активно | Остаток лимита виден в CL-16 (BR-B2B-05) | Система |
| Активно, Лимит исчерпан | HR или администратор отключил сотрудника | Отключено | Будущие сессии без списанного лимита переводятся на личную оплату; без карты отменяются без удержаний не позднее `P-B2B-OFFBOARD-NOTICE` до начала; HR теряет доступ к данным сотрудника (BR-B2B-09) | HR-менеджер, администратор |
| Активно, Лимит исчерпан | Закончился срок программы | Программа завершена | Обрабатывается как отключение всех сотрудников программы (BR-B2B-10) | Система |

HR получает по сотрудникам программы только email и число сессий (DEC-25, BR-PRIV-07). Учётная запись после отключения остаётся у сотрудника как у обычного клиента.

```mermaid

  state "Подготовка" as Registered
  state "Развёртывание" as Deploying

  Deploying --> Configuring: версия развёрнута, первый Супер-администратор создан
  Configuring --> Operational: бренд и домен настроены, проверки пройдены, первый служебный сигнал
```

| Недоступен | Сигнал восстановлен | Работает | — | Система |
| Работает | Раскатка версии после обновления основного prod | Обновление | Резервная копия, миграции, smoke-проверки; все инстансы работают на одной версии | CI/CD |
| Обновление | Обновление успешно или выполнен откат на предыдущий образ | Работает | При откате раскатка на остальные инстансы останавливается; версия видна в ADM-21 | CI/CD |
| Работает, Недоступен | Договор с партнёром прекращён | Прекращение работы | Выгрузка или уничтожение данных — по договору и правовому контуру [ЮРИСТ] | Супер-администратор |
| Прекращение работы | Данные выгружены или уничтожены | В архиве | Запись реестра сохраняется в архиве | Супер-администратор |

Инстанс партнёра работает на том же коде платформы; команда партнёра использует обычные роли RBAC в админ-панели своего инстанса, отдельной роли для партнёра нет (DEC-52).
